# v0.8.13 性能深度诊断与修复报告

## 结论

本次审计发现了一个启动串行化问题、一个会话行 DOM 强引用风险、一个页面范围过大的 MutationObserver，以及外观控制器延迟定时器未完整回收的问题。已经在本分支提交了不改变业务功能的修复，并加入了默认关闭的真实运行时采样通道。

不能在 GitHub 的无 Codex 桌面环境中伪造 CPU 峰值、FPS、长任务数量或堆增长结论。因此，“启动至少降低 20%”和“内存泄漏风险归零”必须以同一台 Windows 机器、同一份 Codex 数据、同一组复现步骤的前后配对采样作为最终验收条件；本报告不把静态源码变化冒充为这些指标。

## 基线与复现

基线版本：\`master\` / \`v0.8.12\`  
修复分支：\`perf/deep-diagnostic-0.8.13\`

启动采样：

1. 设置 \`CODEY_PERF_TRACE=1\`。
2. 设置 \`CODEY_PERF_TRACE_FILE\` 为绝对路径，例如 \`C:\\Temp\\codey-startup.jsonl\`。
3. 完全退出 Codey/Codex 后，从同一启动入口启动。
4. 等待首屏、顶部工具栏和左侧会话栏可交互。
5. 保存 JSONL；每行含 \`stage\`、\`elapsedMs\`、\`sincePreviousMs\`。

运行时采样：

1. 启动时保持 \`CODEY_PERF_TRACE=1\`，探针会按需注入。
2. 通过现有 CDP 9229 会话执行 \`window.__codeyPerformanceProbe.snapshot()\`。
3. 记录启动后 60 秒空闲、打开 20 个会话、连续切换 20 次、滚动长会话、发送一次流式回复五个场景。
4. 对比 \`longTasks\`、\`frame\` 和 \`memory\`；Chrome/Chromium 不提供 \`performance.memory\` 时标记为不可用，不用其他指标替代。

内存回归：

1. 在同一场景开始前和结束后各保存一次 DevTools/CDP heap snapshot。
2. 对比 detached DOM nodes、监听器、定时器闭包和 Codey 自有缓存。
3. 至少重复三轮“打开会话 → 切换 → 返回 → 删除/虚拟化”后再判断趋势。

## 问题清单

### 高优先级：启动前置阶段串行等待

复现路径：启动 Codey，使用启动 JSONL 对比 \`launch_codey_inner.*\`、\`runtime_start.*\` 和 \`startup_storage.*\` 事件。

影响范围：启动期间的应用路径解析、CC Switch 路由读取、持久 Provider 读取、注入脚本组装和本地路由监听创建曾经按串行顺序等待；当任意磁盘或线程池操作变慢，会直接推迟 Codex 进程注入和首屏可交互时间。

量化指标：最终指标是配对 Windows trace 的 \`runtime_ready.elapsedMs\`。GitHub headless runner 无 Codex 安装，当前没有真实毫秒值。

已实施修复：

- 独立的应用路径、路由、持久 Provider 读取和注入脚本准备并发执行。
- 本地路由监听创建与启动前存储维护并发执行。
- 存储维护、临时配置写入和 Codex 进程注入的顺序保持不变。
- 所有阶段加入可关闭的耗时标记。

验收：同机同数据重复 5 次，取中位数；只有修复后中位数不高于基线的 80% 才能宣称达到 20% 目标。

### 高优先级：虚拟化会话行的强引用保留

复现路径：加载大量会话，反复切换左侧栏或滚动触发虚拟化，随后执行 heap snapshot；旧实现的 \`threadUpdatedAtRows\` 会在下一次扫描前继续持有脱离 DOM 的行。

影响范围：长期运行和高频会话切换，可能使脱离 DOM 的行及其闭包暂时不能回收。

量化指标：修复后 Codey 自有跟踪行集合最多 2,048 个；removedNodes 会立即释放子树中的行引用。最终仍需 heap snapshot 验证 detached-node 数量不随轮次增长。

已实施修复：

- 以 2,048 为上限的有序集合。
- 在 \`MutationObserver.removedNodes\` 路径立即清理整棵子树。
- 保留已有的断连行清理逻辑。

### 高优先级：会话工具观察范围过大

复现路径：在流式输出、左侧栏虚拟化和切换会话同时发生时观察 renderer 的长任务；旧实现对 \`document.documentElement\` 监听属性与子树变化。

影响范围：无关的窗口级 DOM 变化会进入 Codey 会话工具过滤器，增加 MutationRecord、选择器和增量扫描压力，可能放大“点击会话后卡住”的问题。

量化指标：观察根从整棵 document 限制为 \`#root\`（找不到时才回退 document）；具体 CPU/长任务毫秒数必须用运行时探针测量。

已实施修复：

- 会话工具 MutationObserver 绑定 \`#root || document.documentElement\`。
- 保留属性白名单、根数量上限和 250ms 最大扫描延迟。
- 没有改变会话按钮、导入、删除和时间戳功能。

### 中优先级：外观控制器延迟回调未完全回收

复现路径：重复加载/销毁外观控制器并在 3 秒内导航或刷新。

影响范围：最多四个延迟同步回调可能在旧控制器销毁后短暂执行；通常不会形成永久泄漏，但会造成无效布局读取和重复挂载检查。

量化指标：修复后所有四个回调句柄均可在 \`destroy()\` 中取消，集合清空。

已实施修复：集中跟踪延迟定时器并在销毁时逐个取消。

### 中优先级：CDP 注入等待与首屏耦合

复现路径：启动期间 Codex renderer 资源加载变慢或 CDP 页面暂时不可发现，观察 \`runtime_injection.begin\` 到 \`runtime_injection.complete\`。

影响范围：注入是功能所需，但当前仍在启动链上；慢时会拉长首屏，失败路径还可能进入重试/清理。

处理计划：

- 用已加入的 trace 先量化 discovery、bridge、overlay verify、status read 四个子阶段。
- 若注入占启动中位数 20% 以上，下一步将“可选功能注入”拆成基本可用模式与增强模式，保证 Codex 首屏先可用；在功能验证完成后再启用可选脚本。
- 不在没有真实 trace 前擅自缩短超时或取消清理，避免重新引入启动后透明/失效问题。

### 低优先级：固定频率的后台刷新

处理计划：

- 用探针确认额度、运行状态和会话时间戳刷新是否在隐藏窗口仍发生。
- 对不可见页面继续保持暂停，对返回窗口采用单次合并刷新。
- 只有确认造成长任务或 CPU 峰值后才调整频率。

## 回归验证

GitHub Actions 的 \`Performance audit\` 工作流会：

- 在 GitHub 侧检出当前提交和基线提交；
- 执行现有 JavaScript 测试；
- 构建注入 overlay；
- 生成前后源码/构建指标 JSON 与 Markdown artifact。

现阶段 CI 不具备 Codex 桌面进程、用户数据、GPU 合成器和可用账户，因此不声称已经完成 Windows 的启动 20% 或堆快照验收。真实 Windows 采样完成后，应把五场景的中位数、P95、长任务总时长、最大帧间隔、heap used 增量和 detached-node 增量补入本报告。

## 变更边界

本分支只通过 GitHub 文件与 Actions 修改/验证；不修改系统壁纸、不改 Codex 安装包 \`app.asar\`，不改变原有业务功能。性能探针仅在显式设置 \`CODEY_PERF_TRACE=1\` 时启用，普通启动不会常驻采样。
